SEC-01 // OVERVIEW

Overview

The voter authentication system is a standalone verification unit built around an ESP32. It asks for two independent factors before a voter record is accepted: the unique QR code printed on the voter list, and a fingerprint match against the enrolled user.

The ESP32 runs an asynchronous web server, so the verification result appears in real time on the interface instead of only on a serial monitor. Every attempt — successful or rejected, along with voter details and system status — is pushed to a Google Sheets audit trail through Google Apps Script.

The design target is narrow and specific: stop unauthorized access, stop duplicate voting, and catch identity mismatches where the QR record and the person at the desk do not belong together.

SEC-02 // PROBLEM & SOLUTION

Problem and solution

ISSUE
  • Unauthorized access — a voter card or record on its own proves very little about who is standing at the desk.
  • Duplicate voting — the same record can be presented twice if nothing tracks what has already been used.
  • Identity mismatch — the QR entry and the person presenting it can belong to different voters.
APPROACH

Require both factors in the same check: the QR code taken from the voter list identifies the record, and the fingerprint confirms the person. A mismatch is rejected instead of being resolved manually.

Keep the operator in the loop with a live web interface on the ESP32, and log everything to a Google Sheets audit trail so decisions can be reviewed afterwards.

SEC-03 // HOW IT WORKS

How it works

  1. 01 Present the QR code. The code taken from the voter list is scanned first, which pulls up the voter record for that entry.
  2. 02 Place the finger. The fingerprint sensor captures the print and the ESP32 matches it against the enrolled template.
  3. 03 Both factors must agree. The QR record and the fingerprint have to belong to the same voter — anything else is a mismatch and is refused.
  4. 04 Result shown in real time. The asynchronous web server on the ESP32 updates the authentication result on the interface as soon as the check completes.
  5. 05 Duplicate attempts are caught. A record that has already been authenticated cannot be used a second time.
  6. 06 Everything is logged. Attempts, voter details and system status are written to Google Sheets through a Google Apps Script endpoint, creating the audit trail.

SEC-04 // KEY FEATURES

Key features

  • Two independent factors — something from the voter list (QR) and something from the person (fingerprint).
  • Real-time authentication result served by an asynchronous web server running on the ESP32 itself.
  • Cloud audit trail in Google Sheets via Google Apps Script, capturing attempts, voter details and system status.
  • Explicit rejection paths for unauthorized access, duplicate voting and identity mismatch.
  • Single-board implementation: the same ESP32 performs the verification and serves the operator interface.

SEC-07 // WHAT I LEARNED

What I learned

  • A verification system is only as strong as its record keeping — logging rejected attempts matters as much as logging the successes.
  • An asynchronous web server is what makes a microcontroller feel like an appliance: the interface stays responsive while the sensor work happens in the background.
  • Small cloud glue layers such as Apps Script are enough to give a hardware project a real audit story without running a backend.
